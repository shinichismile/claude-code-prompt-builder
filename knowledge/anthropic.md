## 1. 基本構造（Basic Prompt Structure）

優れたプロンプトは「Human Turn」と「Assistant Turn」で構成される。

- **Human Turn**: 指示・コンテキスト・データをすべて含む
- **Assistant Turn（Prefill）**: 期待する出力の書き出しを先に書くことでフォーマットを強制できる

```
Human: [コンテキスト + 指示 + データ]
Assistant: [ここに書き出しを入れると出力形式を制御できる]
```

**ポイント**: 最も重要な指示は**最初と最後**に繰り返すと効果的。

---

## 2. 明確・直接的な指示（Clear & Direct Instructions）

曖昧な表現はAIの誤解を招く。常に具体的・直接的に書く。

| 悪い例 | 良い例 |
|--------|--------|
| 良い文章を書いて | 200字以内で、小学生でもわかる言葉で書いて |
| なるべく詳しく | 箇条書き5項目で、各項目2文以内で |
| 適切に翻訳して | ビジネスメール向けの丁寧な日本語に翻訳して |
| できれば早めに | ステップ1から順番に、各ステップで結果を確認しながら |

**ルール**: 「なるべく」「できれば」「良い感じに」は使わない。数字・形式・条件で具体化する。

---

## 3. ロール設定（Role Assignment）

冒頭に役割を明示すると、AIがその専門家として振る舞う。

```
あなたは10年のキャリアを持つシニアソフトウェアエンジニアです。
コードレビューでは、まず全体設計とセキュリティを確認し、
次にパフォーマンス、最後に可読性の順で指摘します。
```

**効果**: 同じ質問でも、役割設定があると回答の深さ・専門性・スタンスが大きく変わる。
**注意**: 「アシスタント」「AIモデル」といった曖昧な役割は効果が薄い。具体的な専門家像を書く。

---

## 4. データと指示の分離（Separating Data from Instructions）

処理対象のデータと指示を混ぜると、AIが混乱する。XMLタグで明確に分離する。

```xml
<document>
  [処理対象のデータ・テキスト・コードなど]
</document>

<instruction>
  上記のdocumentを3つの要点に要約してください。
  各要点は1文で、箇条書きで出力してください。
</instruction>
```

**応用パターン**:
- `<context>` — 背景情報
- `<task>` — 指示本体
- `<example>` — 例示
- `<constraints>` — 制約事項
- `<format>` — 出力形式

---

## 5. 出力フォーマット制御（Output Formatting）

出力の形式・長さ・構造を明示的に指定する。

**形式指定の例**:
```
以下の形式で出力してください：
- 形式: Markdown（見出し・箇条書き使用）
- 長さ: 500字以内
- 言語: 日本語
- 構造: 概要（1文）→ 詳細（3項目）→ まとめ（1文）
```

**Prefillによる強制**:
Assistant Turnの書き出しに ` ```json\n{` と書くと、JSONフォーマットで出力させられる。

## 6. 段階的思考（Step-by-Step Reasoning）

「ステップバイステップで考えてください」を追加するだけで、複雑なタスクの精度が大幅向上。

```
この問題を解く前に、まず考え方を <thinking> タグの中に書いてください。
その後、最終的な回答を出力してください。

<thinking>
[AIがここで思考過程を整理する]
</thinking>

[最終回答]
```

**効果が高いタスク**: 数学・論理パズル・コードのデバッグ・複雑な分析・意思決定

---

## 7. Few-shot 例示（Few-shot Examples）

例を1〜3個見せるだけで出力品質が大幅に向上する。

```
以下の形式で変換してください：

例1:
入力: 「今日はいい天気ですね」
出力: "The weather is nice today."

例2:
入力: 「ありがとうございます」
出力: "Thank you very much."

では以下を変換してください：
入力: 「お疲れ様でした」
出力:
```

**使い分け**:
- Zero-shot（例なし）: シンプルなタスク・汎用的な作業
- Few-shot（1〜3例）: 特定のフォーマット・専門的なタスク・スタイル指定

---

## 8. ハルシネーション防止（Avoiding Hallucinations）

AIが存在しない情報を作り上げる「幻覚（ハルシネーション）」を防ぐための制約。

必ず以下のいずれかを含める：

```
制約:
- 確信が持てない情報は「〜の可能性があります」と明記してください
- わからないことは「わかりません」と答えてください。推測で補わないでください
- 情報源や根拠がない場合は、その旨を明示してください
- 提供された情報のみを使用し、外部の知識で補完しないでください
```

## 9. プロンプトチェーン（Prompt Chaining）

複雑なタスクを小さなステップに分割して連鎖させる手法。

```
ステップ1: 要件を整理する
  → 出力: 要件リスト

ステップ2: [ステップ1の出力]を元に設計を作る
  → 出力: 設計書

ステップ3: [ステップ2の出力]を元に実装する
  → 出力: コード

ステップ4: [ステップ3の出力]をテストする
  → 出力: テスト結果
```

**メリット**: 各ステップの精度が上がる・どこで失敗したかわかる・途中で方向修正できる

---

## Anthropicの「80/20ルール」

失敗するプロンプトのほとんどは、以下4つの修正で解決できる：

1. **ロールを設定する** — 「あなたは〇〇の専門家です」
2. **具体的に書き換える** — 数字・形式・条件で明確化
3. **例を1つ追加する** — Few-shot 1例で精度が上がる
4. **「ステップバイステップで」を追加する** — 複雑な問題に効く

## Claude 特有のベストプラクティス（Claude Code / Cowork 向け）

- `CLAUDE.md` にプロジェクトの背景・制約・好みを書いておくと、毎回説明しなくてよい
- スキルとして作ると、`/スキル名` で呼び出せる繰り返しワークフローになる
- フックを使うと、ファイル編集後の自動フォーマットやコミット前のリントが自動化できる
- サブエージェントを使うと、複数のタスクを並行して処理できる
